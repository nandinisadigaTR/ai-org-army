Message Flow

Producer → POST /notify → Notification API
  → Write to PostgreSQL (notification_id + seq)
  → XADD to Redis Stream notifications:{userId}
  → Delivery Worker XREADGROUP
  → Check revocation set
  → If online: PUBLISH to Redis Pub/Sub → Gateway fans out to local WS
  → Client receives {notification_id, seq, payload}
  → Client sends {type: "ack", seq: N}
  → Gateway XACKs stream entry

Offline path:
  → No connection in registry → stays in Stream unacked
  → On reconnect: client sends last_seq → XRANGE replay

Cross-Agent Debates (What Makes ai-org Valuable)

These are architecture decisions that emerged from agents challenging each other — not from a single perspective.

Debate 1: NATS JetStream vs Redis Streams

CTO: Initially specified NATS JetStream for durable messaging.

Parent (me): Provided 2026 benchmark data — Redis Streams is simpler (one fewer dependency, 480K msg/s, you already run Redis).

QA: Caught the divergence when Senior Dev's code used Redis Streams but CTO specified NATS.

✓ Resolved: Redis Streams for MVP, NATS JetStream V2

CTO accepted. Senior Dev designed IMessageBroker abstraction so the swap is one adapter change. DLQ handling stays inside the adapter impl.

Debate 2: ALB vs NLB

CTO: Specified NLB (L4, least-connections) — better connection distribution for long-lived WS.

DevOps: Pushed back — ALB gives L7 health checks (catches deadlocked gateways), WAF integration, native K8s Ingress. NLB only at 200K+.

✓ Resolved: ALB with "least outstanding requests"

CTO revised after DevOps's evidence. ALB's least_outstanding_requests routing algorithm compensates for connection skew. Crossover to NLB at 200K-500K connections.

Debate 3: JWT Mid-Session Expiry

QA: Flagged as security gap — JWT validated only at handshake means revoked users keep receiving notifications.

CTO: Identified as pre-ship blocker.

✓ Resolved: Dual mechanism — timer + in-band refresh

Senior Dev designed: server-side timer (60s warning → hard disconnect at expiry), in-band token refresh over WS, Redis revocation set checked per delivery. Token swap attack prevented by validating sub claim matches.

Debate 4: Backpressure / Slow Consumer

QA: Flagged as OOM risk — what happens when a client can't read fast enough?

✓ Resolved: Buffer → Drop → Disconnect

100-message per-connection queue cap. Drop current message on overflow (don't reorder). 3 consecutive strikes → ws.close(4008, "slow_consumer"). Safe because Redis Streams replays on reconnect.

IMessageBroker Interface (V2 Migration Path)

interface IMessageBroker {
  publish(subject: string, payload: NotificationPayload): Promise<void>
  consumeFrom(subject: string, group: string, lastSeq: string,
    handler: (msg: BrokerMessage) => Promise<void>): Promise<void>
  ack(subject: string, group: string, msgId: string): Promise<void>
  close(): Promise<void>
}

Connection Draining (Zero-Downtime Deploys)

1. preStop: sleep(10)           # Wait for ALB endpoint propagation
2. SIGTERM handler:
   - Stop accepting new WS upgrades
   - Send close frame 1012 (Service Restart) to all clients
   - Wait for in-flight acks (max 70s)
3. terminationGracePeriodSeconds: 90  # preStop(10) + drain(70) + buffer(10)
4. Client reconnect: base × 2^attempt + rand(0, 1000ms), cap 30s
